# Lead auditor verification notes

- EXT-01 (peer-initiated Rekey): CONFIRMED at core/src/network/session.rs:1221 — `Transport::receive` handles `ProtocolMessage::Rekey` with no check that the sender is the rekey initiator (host). Honest clients never send Rekey (`is_rekey_initiator` false), so the reachable effect is a malicious/buggy peer forcing rotations; a client Rekey crossing a host-initiated one derives K(A,B) vs K(B,A) and desyncs the session. Impact: the peer can only break its own session (it could also just hang up), so severity downgraded to Medium (robustness/spec-violation), not High. Fix: in receive(), if `self.is_rekey_initiator` (we are host) reject an inbound Rekey (log + drop or end session). Related: CRYPTO-06 / NET-03 (only one previous key retained).

- TUI-02 (party-trust sends credentials to an unchecked key): CONFIRMED at client/src/tui/app/cmd_party.rs:63-99 — the trust step reconnects with `expected_fingerprint: None, trust_new_identity: true`; `PendingPartyJoin` (mod.rs:21-25) does not keep the fingerprint the user was shown.
  ALSO AFFECTS THE DESKTOP: desktop/src-tauri/src/commands/party.rs:332-347 passes `pinned` (only a *saved* pin) and `trust`; on a first join there is no pin, so the second connection's key is not compared to the one the user verified either. Combined with SRV-05 (the SAS is per-connection and never shown by the server), the first-join verification step currently protects nothing. One fix for both: `NeedsVerification` returns the fingerprint; the trust call passes it back as `expected_fingerprint` (TUI: store it in PendingPartyJoin; desktop: add a `fingerprint` arg to party_join, single-word per the arg-naming rule) so the credential-bearing connection must present exactly the verified key; and show the server fingerprint (not a per-connection SAS) for out-of-band comparison. Severity: High.

- TAURI-31 (export onto the source truncates identity.json): CONFIRMED at desktop/src-tauri/src/commands/auth.rs:225 — `tokio::fs::copy(&source, &dest)` with no `same_file` check (canonicalize both and compare, or compare dev+inode) and no atomic temp+rename. The auditor verified std::fs::copy(p, p) truncates to 0 bytes on Linux. Needs the user to pick the live identity.json in the save dialog — unlikely, but the result is the permanent loss of the only key to the history. Keep Medium; fix is S (refuse when dest canonicalizes to source; write via write_file_atomic).
- TAURI-30 == APP-01 (unreadable history silently overwritten): two independent auditors reached the same conclusion from both the desktop and TUI side — treat as one High, top of the list.
- TAURI-01 == TUI-02 == SRV-05 (community first-join verification binds nothing): see entry above; one High.
- EXT-02 (export promises identity+history): PARTLY REFUTED by the Tauri auditor — App.jsx:268 is a code comment, not UI copy; the real gap is that the UI never says conversations/contacts/trust are excluded and there is no history backup (TAURI-33). EXT-03/EXT-04/EXT-05 CONFIRMED (TAURI-32/31/34).

- UI-02 (screen shows A, composer sends to B): CONFIRMED in desktop/src/App.jsx — `openConv` (~284-299) and the poll `refresh` (~209-216) both `setActive(...)` from an awaited `getConversation(id)` with no check that `id` is still the active conversation, while `send()` (~301-307) sends to `activeId`. Clicking A then B quickly, or a refresh response for the previous conversation landing after a switch, leaves A's messages on screen with B as the recipient. Fix (S): before setActive, `if (activeIdRef.current !== id) return;`; and have send() target the id of the conversation actually displayed (`active.id`) — or refuse when `active.id !== activeId`. High (misdirected message in an E2E messenger).

- JOURNEY-01 == TAURI-30 == APP-01 (unreadable history overwritten with empty state): CONFIRMED, CRITICAL. Chain: desktop/src-tauri/src/commands/auth.rs:80-83 sets the history key then only `warn!`s when `load_history_auto` fails; `persist_history` (lib.rs:128-145) saves whenever a key is set ("an unlocked but empty history IS saved on purpose"); `saved_sig` starts `None` (lib.rs:451) so `save_history_if_changed` (lib.rs:728-735) writes on the first eligible tick. Result: every conversation, contact, trust state and setting is replaced by an empty file, atomically and silently. Triggers are ordinary: downgrade after a newer build wrote a newer version string or an enum variant this build lacks, a OneDrive placeholder not available offline, bit-rot, or an identity restored from a backup that does not match the history. Same pattern in the TUI (autosave). Fix (M): on any load failure, (a) move the file aside to `history.json.enc.unreadable-<timestamp>` — never delete it — and (b) set a sticky `history_load_failed` flag that makes `history_snapshot()` refuse to produce a snapshot, surfaced in `auth_status` so the UI explains what happened and offers retry/keep-aside; plus a regression test that a failed load never results in a write. This mirrors the identity.json rule already in CLAUDE.md.

- CRYPTO-01 (PEM preamble desync -> identity spoofing): CONFIRMED BY EXECUTION on main @ 62b952f. A throwaway integration test built `"x" + victim_pem + "\n" + attacker_pem`: `fingerprint_pubkey(crafted) == fingerprint_pubkey(victim)` → true, while `pem_decode_public(crafted) == attacker` → true. So the fingerprint every trust decision uses names the victim while the signature is verified with the attacker's key. CRITICAL, affects all released versions (P2P TOFU, Party pins, Party member/Owner re-admission, signed invites). Fix (S): compute fingerprints from the parsed key's SPKI DER, and require the PEM to equal its canonical re-encoding; regression tests for each path. Needs a security advisory. (Test file removed afterwards; nothing committed.)

- QUAL-01 (crafted v1 invite panics the app): CONFIRMED by reading core/src/core/crypto.rs:78-82 — `&s[begin + len("-----BEGIN PUBLIC KEY-----")..end]` with `begin`/`end` from two independent `find`s; when END precedes BEGIN the range start exceeds its end and the slice panics; release `panic = "abort"` kills the process. Reached by pasting a v1 invite (decode_unsigned -> check_fingerprint_binding) before any PEM parse. Same root cause and same fix as CRYPTO-01 (fingerprint from the parsed key). High (remote-triggered crash by a pasted link), fold into the CRYPTO-01 fix.
- Working tree note: the code-quality auditor reported Cargo.lock/deny.toml modified and an untracked zz_lead_pem_check.rs; that was a stale view — those were committed (49a4e6e) and the throwaway test was removed; `git status` is clean.

- EXT-12 (deleting the host placeholder re-hosts): CONFIRMED. desktop/src-tauri/src/commands/chats.rs:558-564 calls `ChatManager::delete_chat` directly, which does not special-case `is_host_placeholder`; `check_rehost_needed` (client/src/app/chat_manager/mod.rs:461-475) returns true whenever `is_hosting && hosting_port.is_some()` and no placeholder exists, so the 1.5 s tick re-listens. The TUI's `disconnect_selected` does call `stop_hosting()` for a placeholder — the desktop does not. Fix (S): make `delete_chat` (in the manager, so both shells get it) call `stop_hosting()` when the deleted chat is the placeholder.
- EXT-14 (lock → unlock never resumes hosting): CONFIRMED. desktop/src-tauri/src/commands/connect.rs:117-127 calls `stop_hosting()` on lock, which clears `is_hosting` and `hosting_port`; unlock only clears the flag, and `check_rehost_needed` needs both. Fix: on lock, remember the port (e.g. `suspended_hosting_port`) instead of clearing it, and restore on unlock; strengthen `lock_stops_hosting_and_unlock_allows_rehost` to assert the listener comes back.
- EXT-13 (clear_history keeps hosting state): CONFIRMED by reading — `clear_history` (mod.rs:748+) does not touch `is_hosting`/`hosting_port`. Whether clearing history should stop hosting is a product decision; at minimum the placeholder must not be recreated as a "new" conversation silently.
- EXT-11 (self-connection not refused): PLAUSIBLE, not re-traced here; `my_fingerprint` is used by `import_contact` only. Fix: in `handle_tofu_verification`, refuse a peer whose fingerprint equals our own.
